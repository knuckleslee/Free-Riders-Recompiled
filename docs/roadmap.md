# Roadmap

## 首次啟動體驗：讓第一次啟動的玩家也流暢（比照 Unleashed Recomp）

目標：玩家第一次啟動就不會在遊戲裡頓卡。做法和 Unleashed 相同：發行版附上
「要建哪些 pipeline」的清單，第一次啟動時在載入畫面把需要的東西全部準備好，
進遊戲時已經是熱的。

現況：
- `src/native_pipeline_cache.cpp` 的磁碟 cache 只有 Vulkan 有，D3D12 沒有。
- 已實作（commit 3872cb4）：執行時記錄每條 pipeline 到
  `pipeline-cache/pipelines-<backend>.bin`，下次啟動在背景預先建立
  （細節見 `docs/benchmark.md`「階段 D」）。只對第二次以後的啟動有效。

要補的三件事，缺一不可：
1. **覆蓋率錄製**：讓遊戲自己把所有場景都走過一遍，產出一份完整的 manifest。
2. **隨發行版附上 manifest**：內容只有著色器雜湊與狀態，不含遊戲資料，可以放進 repo。
3. **第一次啟動的準備畫面**：在啟動器顯示進度，並行做完兩件事再進遊戲：
   a. 著色器轉譯：目前是遊戲載入時才即時轉譯並用 DXC 編譯（`runtime_shader_cache`）。
      轉譯結果來自玩家自己的遊戲檔案，**不能隨發行版附上**，只能在玩家機器上產生，
      所以要移到準備畫面，不能留到遊戲中。
   b. pipeline：依 manifest 全部建好。

技術注意：
- manifest 以著色器 container 的雜湊（`shader_identity`）對應，需驗證不同機器、
  不同遊戲版本（地區）下一致；不一致的記錄直接略過，不影響正確性。
- 記錄的格式與 pipeline 的鍵一旦改動，舊 manifest 就要重錄，所以要等格式穩定、
  階段 D 在 PC 上驗證沒問題之後再錄。
- 不同 GPU 的驅動各自有 pipeline 編譯快取；manifest 與 GPU 無關，換 GPU 只是
  編譯時間不同。

### 「夠了」的標準

不求窮舉：一條 pipeline 由遊戲執行時設定的狀態組成，排列數量大、
大部分永遠不會出現，沒有辦法列全，也不值得。標準是**新玩家感覺不到**，
並且可以量：

- 量法：用「乾淨安裝＋隨發行版附的 manifest」跑一場完整的 Free Race，
  統計「因為當場建 pipeline 而超過 30 ms 的格」（`pipeline_ms` 大於 0 且該格
  超過 30 ms；`benchmark_summary.py` 之後要補這個欄位）。
- 目標：每場 0 格，最多容許 1～2 格。
- 為什麼是這個數字：目前（沒有 manifest）一場比賽約有 8 格因編譯而花
  87～91 ms、整格 150～180 ms（2026-09-30 的 log，i7-6850K／D3D12）。
  平均只占一場 3468 格的 0.2%，所以看平均 fps 看不出來，但一格 150 ms
  相當於 9 個畫面停住，是玩家會注意到的頓一下；而不到 30 ms 的一格
  （不到 2 個畫面）通常感覺不到。
- 其他 pipeline 平均只要約 0.15 ms，不必追求全部預建。
- 達不到目標時，先看 `manifest_stats.py` 的新增量決定補錄哪裡，不要先加機制。

### 之後補錄

manifest 只會增加、不會重複（遊戲開機時讀入，已有的記錄不會再寫）。所以補錄很簡單：

1. 把發行版的 manifest 複製到 `pipeline-cache\`，照常玩；新出現的 pipeline 會接在後面。
2. 用 `scripts/manifest_stats.py 舊檔 新檔` 看新增了多少、哪些著色器是新的。
3. 來自不同工作階段或機器的檔案，用 `scripts/merge_pipeline_manifest.py a.bin b.bin -o merged.bin` 合併去重。
4. 合併後的檔案放回發行版。

注意：
- 記錄格式或 pipeline 的鍵改動後，舊檔就不能用（讀不懂的記錄會被略過，不會出錯，只是沒效果）。
- 遊戲版本或著色器轉譯改變，著色器雜湊就不同，舊記錄同樣只是失效。
- 只記「當場建立」的 pipeline，所以補錄時看到的新增，正好就是原清單沒涵蓋到的。
- manifest 只有著色器雜湊與狀態，沒有遊戲資料；玩家有需要時也可以回傳自己的檔案。

### 之後可能要加：沒涵蓋到的 pipeline 不卡畫面（比照 Unleashed 的非同步編譯）

遇到清單沒涵蓋、還沒建好的 pipeline 時，先略過那個 draw、交給背景建好再畫，
而不是當場編譯讓整格停住。代價是那幾格少畫一個物件，換來畫面不卡。
是否需要，取決於錄製後上面的標準能不能達到；涵蓋率夠高就不做。

### 什麼時候做完整錄製

開發初期不做完整版：記錄格式、pipeline 的鍵和著色器雜湊都還可能改，改了舊檔就失效，
整晚的錄製要重來；也還沒有玩家在等這份清單（自己的 PC 玩過一次，第二次起就有自己的）。

現在只做輕量版，目的是**驗證與取得數據**，不是產出發行用的清單：
第一關、一種配置，第二圈開頭存 `lap1.bin`、結算存 `end.bin`，再重開一次確認 log 有
`NATIVE_PIPELINE_PREWARM ... adopted=`（記錄、預建、取用這條路徑有效），
並取得「有多少 pipeline、一圈夠不夠、換配置新增多少」的數字。

完整錄製（多關卡、多配置、任務模式、專屬路線與捷徑）留到準備發行、格式穩定之後。

### 手動錄製的做法（10/1 晚上）

手動玩比腳本可靠：腳本走的路徑固定，遊戲有些狀態（結算、重試、例外按鍵）不會出現。

- 決定 pipeline 的是「著色器＋頂點格式＋混合／深度／模板／裁切狀態」，
  **貼圖、角色的顏色、場景的位置都不算**。所以錄製要涵蓋的是「不同的著色器組合」，
  不是每一種角色×裝備×關卡的排列。
- 同一關：場景物件的 pipeline 與角色無關，跑一次就夠。會不同的只有角色與裝備模型
  （蒙皮頂點著色器、裝備的特效）。所以同一關只需要挑**差異最大**的幾組配置
  （不同裝備類型、不同角色類型），不必全跑。
- 用數據判斷是否跑夠，而不是猜：每跑完一組配置就複製
  `pipeline-cache\pipelines-d3d12.bin`，用 `scripts/manifest_stats.py 前一份 後一份`
  看新增了多少。新增接近 0 就表示這一類已經涵蓋；仍有明顯新增就再換一組不同的配置。
- 任務模式：選同一個場景的任務，主要新增的是任務專用的 HUD／效果與物件，
  同樣比較新增量。
- 之後換別的關卡，場景物件的 pipeline 幾乎都是新的，這部分不能省；
  每關要至少完整跑一次（用一組配置即可），再加上上面挑過的角色／裝備。

選 10/1 晚上錄製的理由：錄製本身不消耗 token（在你的 PC 上跑），
但要等步驟 1 確認階段 D 的記錄與預建沒問題、格式定案；
腳本與合併工具是小工作，節約期間用 Sonnet 做就夠。
準備畫面屬於架構性工作，放到 10/2 之後再做。
