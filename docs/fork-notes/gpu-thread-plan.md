# 參考 Xenia 把繪圖翻譯移出主執行緒：評估與分段計畫

## 現在主執行緒每格做什麼（i5，v0.4.7，比賽 20–75 秒，`par` 的 log）

每格約 780 次繪製，主執行緒花在繪製路徑約 **6 ms**（`cores` 6.1、`all` 5.8；整格 32–38 ms）：

| 項目 | ms | 在哪裡 |
| --- | ---: | --- |
| `renderer().draw()`：pipeline key 與查表、常數／索引寫進上傳環、排進渲染執行緒 | 1.4 | `native_renderer.cpp` `NativeRenderer::draw` |
| 取頂點（gather） | 0.8 | `guest_graphics_hooks.cpp` |
| 常數：從裝置影子複製 8 KB 並位元組交換 | 0.75 | 同上 `constants(1920/6016)` |
| 貼圖查找與上傳 | 0.7 | 同上，`renderer().texture()` |
| DEC3N 頂點重排 | 0.6 | 同上 |
| 索引 | 0.45 | 同上 |
| 頂點位元組交換 | 0.3 | 同上（約一半的繪製用頂點快取，不用交換） |
| 其他（宣告、著色器、狀態讀取） | 約 0.9 | 同上 |

命令錄製本身（`setPipeline`、`draw*`）已經在渲染執行緒上。

## Xenia 的做法與差異

Xenia 的遊戲 D3D 只寫 PM4 封包（暫存器的**增量**寫入），GPU 執行緒維護自己的一份暫存器，逐包翻譯。
我們的 D3D 函式是原生實作，狀態存在客體記憶體裡的裝置影子（常數 8 KB、取樣、渲染狀態），
繪製時一次讀完。

要照 Xenia 搬，主執行緒在繪製時至少要把「這次繪製看到的狀態」交給渲染執行緒。整份 `NativeDraw`
約 9.5 KB，每格 780 次就是約 7.4 MB 的複製，本身就約 1 ms，抵掉大半收益。真正省事的做法是
像 PM4 一樣只送**變動的部分**：常數、取樣、渲染狀態的設定函式各自寫增量，渲染執行緒維護自己的影子。
這等於重寫 `guest_graphics_hooks.cpp`、`guest_graphics_state.cpp` 與 `native_renderer.cpp` 的介面。

## 正確性風險

- **客體記憶體會在繪製後被改寫**：頂點、索引、貼圖都是在繪製時從客體記憶體讀的。延後到渲染執行緒讀，
  遊戲可能已經改寫了。Xenia 靠遊戲遵守 GPU 非同步的規則（fence）；我們的 fence 是照「繪製已同步完成」模擬的，
  要先改成追蹤渲染執行緒的進度。
- 貼圖上傳與解析（resolve）的順序、頂點快取的寫入追蹤，都要跟著改。

## 預估

上限是主執行緒省下約 4–5 ms（6 ms 扣掉至少要做的狀態交接），i5 上約 +12–15%。前提是有一顆空閒核心：
i5 只有 4 核，開了 `all` 之後其他核心更忙，實際可能更少。工作量以週計。

## 分段（每段都能單獨量測、單獨回退）

1. **先量清楚**：在 i5 上用 `profile` 取樣主執行緒，確認上表各項的實際份量（上表是每格計時，不含快取效應）。
2. **只搬不碰客體記憶體的部分**：pipeline key 與查表、上傳環寫入、常數交換。主執行緒只複製原始常數
   （8 KB，不交換）到每格的暫存區，渲染執行緒做其餘的事。上限約 2 ms。
3. **常數改送增量**：`SetVertexShaderConstantF` 等設定函式記錄變動範圍，繪製只送變動的部分。
4. **fence 追蹤渲染執行緒進度**，之後才能把頂點、索引、貼圖的讀取移過去。
